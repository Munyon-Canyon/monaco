# CI

How Monaco runs continuous integration: which checks run, when they run, on what machines, and what it costs. CI is the last line of verification for the whole repo, so it must be deterministic, fast, and small enough that nobody is tempted to bypass it. The checks themselves are defined in [backend-platform.md, CI gates](backend-platform.md#ci-gates) and [Testing](backend-platform.md#testing); this file decides how they are scheduled and paid for.

For the steps of shipping a ticket or running a milestone through these checks, read [Ship a ticket](../how-to/ship-a-ticket.md) and [Run a milestone](../how-to/run-a-milestone.md).

## Decision

1. **CI confirms; it does not discover.** Every check a PR needs runs on the laptop first: `just test backend` (under 90 s) and the lint pre-commit hook. CI reruns the same commands on a clean machine to prove the result does not depend on the author's machine. A red CI run on a ready PR is a bug in the local gate, not a normal step. `monacoctl verify`, every flow against the real binaries, runs only in stage 1's `e2e` job and nightly, never as a laptop or owner step.
2. **Full CI runs only on PRs that can merge.** A PR runs CI when it is not a draft and its base is `main` or the trunk, `staging`. Drafts run nothing, except the Graphite merge queue's own draft PRs, which run stage 2, as does the push to their branch. In a stack, only the top PR runs the suite: `plan` skips every job on a PR that another open, non-draft PR builds on, so its `ci / ci-ok` passes and `monacoctl agents check` is its proof.
3. **No CI on push to `main`.** Branch protection requires the branch to be up to date before merging, so the PR run already tested the tree that lands. The nightly run covers `main`.
4. **One required check.** A final `ci-ok` job aggregates every other job with `re-actors/alls-green`. It is the only check branch protection names, so jobs can be added, split or path-filtered without touching the protection rule.
5. **Filter jobs, never workflows.** Path and draft filters go in job-level `if:`. A workflow skipped by a `paths:` filter leaves its required check pending forever; a job skipped by `if:` reports success.
6. **One macOS job, in stage 1 and the staging indicator only.** `packages/mobile-core` host tests run on Linux. The `ios` job builds the app and runs `MonacoTests` on macOS when a PR touches the app, mobile-core or a flow. The merge queue runs no macOS job. The nightly `qa` job adds the UI tests and screenshots.
7. **Stay on GitHub's free hosted runners while the repo is public.** They are free and unmetered for public repos. [Staying on the free tier](#staying-on-the-free-tier) lists the rules that keep it free, and [Runner options](#runner-options) says what to switch to if the repo goes private or the macOS queue gets long.
8. **Nightly runs the unbounded suites**, and skips the night when `main` has not moved since the last green nightly.

## Why

**The 2,000-minute limit does not apply today.** `Munyon-Canyon/monaco` is public. Standard GitHub-hosted runners, macOS included, are free with no minute cap in public repos ([GitHub billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions)). The Free plan's 2,000 minutes and 500 MB of artifact storage apply only to private repos. What does bind a public repo is concurrency: 20 jobs at once, and only 5 of them on macOS ([limits](https://docs.github.com/en/actions/reference/limits)).

**It would apply the day the repo goes private.** Measured from the last 100 workflow runs (2026-09-23 to 2026-09-27, 3.4 days), with each job rounded up to a whole minute as GitHub bills it ([pricing](https://docs.github.com/en/billing/reference/actions-runner-pricing)):

| Job | Runner | Runs | Average | Billed minutes |
| --- | --- | --- | --- | --- |
| `go` | Linux | 89 | 0.7 min | 104 |
| `changes` | Linux | 57 | 0.1 min | 55 |
| `web` | Linux | 57 | 0.1 min | 55 |
| nightly `alert` | Linux | 11 | 0.1 min | 11 |
| `swift` (mobile-core) | macOS | 89 | 0.8 min | 126 |
| nightly `qa` | macOS | 11 | 13.1 min | 152 |

At that pace a 30-day month is about 2,000 Linux minutes and 3,500 macOS minutes (extrapolated, not measured). As a private repo that exhausts the free quota on Linux alone and adds about $220 a month of macOS at $0.062 per minute. Two findings drive the decisions above:

- Half the Linux bill is rounding. `changes`, `web` and `alert` run for about 6 seconds each and bill a full minute each.
- The `swift` job pays macOS rates for tests that run on Linux, and it runs on every PR, including Go-only ones.

**Most runs were not merge candidates.** 230 of the 284 runs in the last month were `pull_request` runs, which fire on every push to every open PR, drafts and upstack PRs included. Gating on "ready and based on `main`" removes those runs without removing any check from a PR that can merge.

## Check stages

A change passes three check stages. Each stage runs only what the stage before it skipped.

| Stage | Where | Runs |
| --- | --- | --- |

`ci.yml` sets the `stage` input of `ci-jobs.yml` from the head branch (the pushed branch on a push): a branch that starts with `gtmq_` is `queue`, and every other PR is `pr`. `ci-retarget.yml` always passes `pr`. `staging.yml` passes `staging`. Mutation testing runs only in the nightly.

`monacoctl ci affected --base <ref>` prints the packages that `<ref>...HEAD` changes, plus every package that imports one of them, one per line. A package whose tests import a changed package also counts. The command reads reverse dependencies from `go list -deps -json ./...`. It prints `./...` when `go.mod`, `go.sum`, a file under `internal/testkit/`, or any file outside a Go package changed.

Stage 1 reuses a green result only when the diff and the CI definition are both unchanged. The key is `patch-id: <patch_id> ci-id: <ci_id>`. A stacked top PR keys on the whole stack's diff, so a restack that changes a PR below it reruns stage 1. Lower PRs of a stack skip every job anyway.

1. `ci / Plan` computes the patch ID of the PR's diff: `git diff <base>...<head> | git patch-id --stable`. For a stacked top PR, whose base is the PR below it, `<base>` is the merge base with the trunk instead, `git merge-base origin/<trunk> <head>` (`TRUNK_REF` in `scripts/ci/stage1-reuse.sh`), so the patch ID covers the whole stack. With no merge base there is no key and stage 1 runs. A restack that leaves the diff unchanged keeps the patch ID. It also computes `ci-id`, the first 12 characters of `git rev-parse <head>:.github/workflows`, the tree of the workflow files at the PR head. A restack onto a trunk that changed a file under `.github/workflows` changes `ci-id` even when the patch ID stays the same.
2. It finds this PR's last green `ci / ci-ok` among the head SHAs of its 5 most recent distinct runs and reads that check run's output summary. Reuse only saves time, so when a GitHub API call fails, for example on the installation rate limit, `scripts/ci/stage1-reuse.sh` prints a warning and runs the full stage 1.
3. If the summary equals `patch-id: <patch_id> ci-id: <ci_id>`, every stage 1 job skips and `ci-ok` passes. A summary in the old form, `patch-id: <patch_id>` alone, does not match, so that push runs stage 1 again.
4. `ci-ok` stores the current key, `patch-id: <patch_id> ci-id: <ci_id>`, in its own output summary.

Stage 2 never reuses a result. Graphite tests each queued stack once, on a temporary branch whose name starts with `gtmq_` and holds the whole stack, with a draft PR on it. `ci.yml` runs stage 2 on that draft even though it is a draft, and again on the push to its branch. Graphite bases each draft on the draft below it, and when that one lands and its branch is deleted GitHub closes the draft above. A draft closed before GitHub started its `pull_request` run never got one, and Graphite waited for a `ci / ci-ok` that never came (#2844). The push run reports on the same commit, open draft or not. The draft's own run is kept, because a draft whose only `ci / ci-ok` came from the push run, and whose `pull_request` run skipped, never landed (#2868). Graphite tests up to 4 stacks at a time. The PRs of one stack land or fail together. A stage 2 failure drops that stack from the queue and removes its `merge-queue` labels.

## Triggers

```yaml
# ci.yml
on:
  pull_request:
    types: [opened, synchronize, reopened, ready_for_review]
  push:
    branches: ['gtmq_**']
  workflow_dispatch:

concurrency:
  group: ci-${{ github.event.pull_request.number || github.ref }}
  cancel-in-progress: true

jobs:
  ci:
    if: >-
      ${{ github.event_name != 'pull_request' ||
      ((!github.event.pull_request.draft || startsWith(github.head_ref, 'gtmq_')) &&
      !startsWith(github.base_ref, 'graphite-base/')) }}
    uses: ./.github/workflows/ci-jobs.yml
    with:
      stage: ${{ startsWith(github.head_ref || github.ref_name, 'gtmq_') && 'queue' || 'pr' }}

# ci-retarget.yml
on:
  pull_request:
    branches-ignore: ['graphite-base/**']
    types: [edited]

jobs:
  ci:
    if: >-
      github.event.changes.base != null && !github.event.pull_request.draft &&
      (github.base_ref == 'main' || github.base_ref == vars.FEATURE_BRANCH ||
      startsWith(github.event.changes.base.ref.from, 'graphite-base/'))
    uses: ./.github/workflows/ci-jobs.yml
    with:
      stage: pr

# staging.yml
on:
  schedule:
    - cron: '17 * * * *'
  workflow_dispatch:

concurrency:
  group: staging-ci
  cancel-in-progress: false

jobs:
  staging:
    uses: ./.github/workflows/ci-jobs.yml
    with:
      stage: staging
```

- The jobs live in `ci-jobs.yml`, a reusable workflow. Both PR callers name their job `ci`, so every check reads `ci / <job>` and the required check is `ci / ci-ok`. `staging.yml` names its job `staging`, so its checks never stand in for a PR's `ci / ci-ok`. `mobile-core` is itself a call to `ci-mobile-core.yml`, so its check reads `ci / mobile-core / Swift (mobile-core, Linux)`. That split lets the `plan` job's path filter key on `ci-mobile-core.yml` instead of every `ci*.yml`, so a backend PR that only edits `ci-jobs.yml` no longer runs the Linux `mobile-core` job. `ci-ok` still names only job IDs in `needs`, so the required check and `allowed-skips` are unaffected by the extra nesting level. `ios` calls `ci-ios.yml` the same way, so editing `ci-jobs.yml` alone does not run the macOS job. The queue stage runs no macOS job.
- `ci.yml` runs on every PR, so a stacked PR whose base is another ticket branch gets CI on its own diff. `ci-retarget.yml` triggers on every base except a `graphite-base/` branch. Its job runs when the new base is `main` or the trunk, `vars.FEATURE_BRANCH` (`staging`). The job also runs when the old base was a `graphite-base/` branch. No workflow trigger names a milestone.
- No workflow triggers on `merge_group`, because the GitHub merge queue is off. Stage 2 runs on the Graphite queue's `gtmq_` draft PR through the `pull_request` trigger, and on the push to its branch. A `workflow_dispatch` of `ci.yml` on a `gtmq_` branch runs stage 2 too, to rescue a queue draft that never got its check. `pr-format.yml` runs on that draft too, and its `PR format (title, body and commits)` job passes without checking, since each PR passed it on its own head. When `scripts/check-pr-format.py` cannot list the open PRs stacked above and below, it prints a warning and skips only the `Closes`/`Part of` checks against them; every other format check still runs. `scripts/ci/workflow_triggers_test.go` fails if a workflow with a required job filters on `paths` or `paths-ignore` at the workflow level. The Plan job runs it whenever a workflow changes.
- `pr-format.yml` runs the `pr-format` and `pr-size` checkers from the PR's base commit, not from its merge ref. Each job checks out `github.event.pull_request.base.sha`, fetches the head commit, and runs the script from that checkout, with `BASE_SHA` and `HEAD_SHA` in the environment. A PR's own edits to those scripts do not change that PR's verdict, and a stale merge ref, which GitHub serves for a while after a base change, cannot supply an old copy of them (#1090). An edit to `pr-format.yml` itself still takes effect, because GitHub reads the workflow file from the merge ref.
- The script's unit tests run after that verdict, even a failed one, from a worktree of the head commit, so a PR that edits a checker still runs its own tests. The tests come second because the head's tests import the head's checker, and that import could rewrite the base copy before the verdict runs.
- A draft skips the `ci` job. That leaves one skipped check named `ci` and no `ci / ci-ok`, so the PR cannot merge until it is ready and CI passes. GitHub counts a skipped job as a passing required check, so the gate never depends on a skip.
- Inside `ci-jobs.yml`, `ci-ok` uses `always()`, not `!cancelled()`. A run cancelled by a newer push then leaves a failed `ci-ok`, not a skipped one.
- Graphite restacks an upstack PR while its base is a temporary `graphite-base/N` branch, then retargets it with no new push. A bottom PR goes back to `main` or `staging` (seen on #452). An upper PR goes back to the PR below it. `ci.yml` sees neither event. `ci-retarget.yml` runs on both retargets and runs the same jobs, whatever the new base is called. Neither runs the `ci` job while the base is `graphite-base/`. Graphite deletes that branch after the restack, and a run against it left a stale failed `ci-ok` (#838, #839).
- GitHub counts only the newest run of each workflow on a commit. A title or body edit after a retarget, with no push in between, makes a skipped `ci-retarget.yml` run the newest one, and `ci / ci-ok` goes back to "Expected". Rerunning the retarget run does not help. Push the branch to run `ci.yml`. A `ci / ci-ok` from `ci.yml` survives later edits (probed on #648 and #718).
- `edited` is not in `ci.yml`. An edit run there shares the concurrency group, cancels the real run, and leaves a skipped `ci-ok` as the newest check (seen on #493). In `ci-retarget.yml` a title or body edit skips the caller job and creates only a skipped `ci` check.
- `workflow_dispatch` checks do not satisfy a required check (a probe ruleset on #501 stayed blocked with a green dispatched `ci-ok`). Dispatch is only for looking at results on a draft or an upstack branch. `dorny/paths-filter` has no PR base on a dispatch run, so with no `base:` input it falls back to its documented default for non-`pull_request` events: `git merge-base` against the repository's default branch (`staging`). The `filter` step in `ci-jobs.yml` sets no `base:`, so a dispatch run already gets that default and does not run every job unfiltered; no change was needed here.
- `pull_request` does not run while a PR has a merge conflict. Resolve the conflict to get CI.

Ruleset on `main`, which targets `refs/heads/main` by name:

- Require `ci / ci-ok` and `Changelog (checkpoint into main)` from GitHub Actions (integration 15368), so a commit status with the same name from another source does not count.
- Require branches to be up to date before merging.
- Block force pushes and deletion.
- Require approval before running workflows from all outside contributors (`fork-pr-contributor-approval`), not only first-time ones.
- Require a pull request. A promotion from `staging` lands with a merge commit, so `main` gets one merge commit per promotion. `main` has no merge queue. Only the operator merges into it, by hand.

## Staging and main { #feature-branches }

Monaco has one long-lived trunk, `staging`. It is the repo's default branch, so a new PR targets it unless told otherwise. Every ticket PR lands on `staging`, and `staging` reaches `main` through a promotion PR. Nothing cuts a new branch per milestone or per promotion.

The `FEATURE_BRANCH` repo variable is `staging`, and `staging` is the Graphite trunk. `feature_branch = "auto"` in `.monaco/agents.toml` resolves to the `MONACO_FEATURE_BRANCH` env when set, then to `gh variable get FEATURE_BRANCH`, and fails naming both when neither gives a name. `agents-status.yml` passes the variable in as `MONACO_FEATURE_BRANCH`. `agents-status.yml` skips a push to a branch that is not `main` or `vars.FEATURE_BRANCH`. `gardener.yml` checks out `vars.FEATURE_BRANCH` and fails when it is unset.

`scripts/branch-rulesets.sh staging-ruleset` and `scripts/branch-rulesets.sh main-ruleset` print the two rulesets. `scripts/branch-rulesets.sh apply` creates or updates both, with an org admin token.

The `staging` ruleset:

- Targets only `refs/heads/staging`.
- Requires a pull request and allows only squash merges. A person who merges a PR directly therefore squashes it. The Graphite queue merges through its bypass instead, and squashes too.
- Requires `ci / ci-ok` from GitHub Actions (integration 15368). `PR format (title, body and commits)` still runs on every PR but is advisory: a red one shows on the PR and blocks nothing, because `scripts/pr-body.sh` already runs the same check before it sets a body, and the run failed on the shared `GITHUB_TOKEN` rate limit rather than on the PR. The `verify` commit status is not a ruleset check. The agent guard hook refuses `gh pr merge` until the head's latest `verify` status is `success`, from any poster.
- Blocks force pushes and deletion.
- Has two bypass actors: org admins (`OrganizationAdmin`) and the Graphite App, which the Graphite merge queue needs to merge a stack it tested on its own draft PR.

`staging` also has a classic branch protection rule. Its only setting lists the Graphite App under "Allow specified actors to bypass required pull requests". Graphite's queue cannot read rulesets and needs that rule for its optimizations. The ruleset holds every real rule.

### Land a PR on staging

PRs land through the Graphite merge queue. The GitHub merge queue and the repo's auto-merge are off. Two labels drive the queue:

- `merge-queue` queues a PR. A stack is queued when every PR in it carries the label. Removing the label by hand does not reliably take the PR out: Graphite re-adds it from its own state. `monacoctl agents dequeue <top-pr>` removes it from every PR and waits until Graphite lets go. The agent guard hook blocks `gt submit`, `gt modify`, `gt restack` and `git push` on a stack while any of its PRs carries `merge-queue`, is named in an open `gtmq_` draft, or was taken by Graphite less than 30 minutes ago with no closed draft since. Graphite removes the label when it takes a PR and opens the draft minutes later. `monacoctl agents land-stack <top-pr>` adds it to each PR of a stack, bottom to top, once each has a green `ci / ci-ok`. A head with leftover cancelled or failed workflow runs keeps its PR out of the stack's queue draft, so Graphite queues a shorter prefix and the rest wait for later passes (inferred from #1493 to #1495, not from Graphite documentation). `land-stack` reruns those runs before it labels, refuses with the run's name and URL when a rerun fails again, and afterwards prints which PRs the draft holds. Before it arms or labels a stack, `land-stack` refuses one whose flows (mapped from every PR's changed files as `monacoctl flows --affected` maps them, except that an added error code counts only for the flows whose outcomes name it) could differ in the queue from what stage 1 proved, and the refusal names the action. If a flow is also in a stack that already carries the queue label, it prints `not landing #N: flow 07 is in queued stack #M. Wait for #M to land, then run land-stack again`. If a flow changed on `staging` since the stack's merge-base, it does not ask for a restack. It dispatches `flows-verify.yml` from `staging`, which merges the top PR's head onto the current `staging` SHA, builds `monacoctl` from the merge and runs `monacoctl verify flow <id>` for exactly the flows that moved on one Linux runner, instead of a restack and a full stage 1. The run reports a `flows-verify` commit status on the top head whose description is the key, `flows 07 13a on staging <sha>`, so `land-stack` and `agents watch` read back only a run for that head, that flow set and that `staging` SHA. While it runs, `land-stack` arms the stack with `waiting on flows-verify of flows 07 on staging <sha>: flow 07 changed on staging since this stack's base (#M)` and `agents watch` prints `armed stack #N started flows-verify ...` when it dispatches one. When it passes, `agents watch` lands the stack. When it fails, including a merge conflict with `staging`, the stack is disarmed with `not landing #N: flow 07 changed on staging since this stack's base (#M), and flows-verify failed on staging <sha> (<run URL>). Restack with gt and rerun stage 1, then run land-stack again`. If `staging` moves again before it lands, the key no longer matches and the next pass dispatches a new run, as it does for a run still pending after 30 minutes. A key longer than a status description (140 characters) falls back to the restack refusal. The targeted run covers only the moved flows. Unit tests and the coverage gate on the merged code stay with the push to `staging` (`staging.yml`). A stack that touches no flow skips these checks, and an armed stack gets the same checks when `agents watch` lands it. While Graphite holds a queued stack, `agents watch` prints `#N labeled, waiting for Graphite`. When that wait passes `[watch] stuck_after` in `.monaco/agents.toml` (12 minutes by default) and no open `gtmq_` draft lists the stack's top PR, it prints `stack #<top> stuck in the queue <age>: no live queue draft; run monacoctl agents dequeue <top> then land-stack <top>` once per wait. It stays silent while every queue slot (`queue_concurrency`) holds a draft, and it never dequeues or relabels on its own. Graphite lost #2677, #2683 and #2832 this way when their draft closed before CI ran (#2844). `monacoctl agents forecast` prints a `flows: <id> #<bottom> #<bottom>` line for each flow that more than one open stack touches, so the clash shows before `land-stack`. The label name is `queue_label` in `.monaco/agents.toml`, `merge-queue` by default. An agent never adds it by hand, and the agent guard hook blocks that. A person landing by hand runs `gh pr edit <n> --add-label merge-queue` on each PR, bottom first.
- `fast-track` moves a PR to the front of the queue. Only a person adds it, and only to a PR under 100 counted lines that touches nothing under `apps/backend/`, `.github/` or `docker-compose.yml`: a jump is safe only when the PR cannot break what it passes, and stage 2 runs nothing heavy for it. The PR size check fails any other `fast-track` PR, and CI removes the label. The agent guard hook blocks an agent from adding it.

The queue runs stage 2, the light build check, on the topmost PR of each stack ([Check stages](#check-stages)), then squashes each PR into one commit on `staging`: the PR title with ` (#N)`, a blank line and the PR body, authored by the PR author. Graphite then closes the `gtmq_` draft and marks each original PR closed, not merged. A PR counts as landed when it is merged, or when it is closed and `staging` has a commit whose first line ends with ` (#N)`, or else its head commit is on `staging`. `monacoctl agents` reads it by that rule. The squash commit carries the PR body, so `Closes #<n>` in the body closes the ticket once the commit reaches `staging`, the default branch.

The ruleset also allows a direct squash merge once stage 1 is green. Stage 2 then never runs on that change. Agents never merge directly: the agent guard hook blocks `gh pr merge` into `staging`.

### Promote staging to main

A promotion is a PR from `staging` into `main` with the `integration` label. The operator merges it by hand with a merge commit, not a squash. A merge commit keeps `staging` and `main` in one history: `staging` keeps going after the merge, and the next promotion carries only what landed since.

A promotion PR must carry a backend changelog entry. The `Changelog (checkpoint into main)` job in `pr-format.yml` runs `scripts/check-changelog.py <base> <head>`, which fails when the diff changes `apps/backend/**` without changing `apps/backend/CHANGELOG.md`, or when that file has an empty `## [Unreleased]` section and no `## [checkpoint N] - <date>` section added by this diff. Before opening a promotion, land a PR on `staging` that renames `[Unreleased]` to `[checkpoint N] - <date>` and opens a new `[Unreleased]` holding only an empty `### Added` heading, which `monacoctl gen module` needs. The check counts only `- ` entries, so that heading alone is still an empty section. A PR into `main` without the `integration` label skips the job, and a skipped required check counts as passing.

## Shared files { #shared-files }

`monacoctl agents batch` keeps two tickets out of one batch when their `Touches` globs overlap. Most backend tickets add a route, a flow row, a migration or an event, so their `Touches` overlap on the same few files even when the tickets don't conflict in substance. `[batch] shared` in `.monaco/agents.toml` lists those files. A pair of overlapping globs that both lie inside a `shared` glob does not count as an overlap, and `batch` prints a `shared:` line for it. A glob that reaches past a shared file, such as `apps/backend/*`, still counts.

| Shared glob | Why a conflict there is safe |
| --- | --- |
| `apps/backend/internal/platform/httpx/api/**/*.gen.go`, `apps/backend/sqlc.yaml`, `apps/backend/.golangci.yml`, `apps/backend/cmd/api/**`, `docs/reference/**` | Generated by `go generate ./...` (`sqlc.yaml` mixes a hand-written header with a generated module list and stays on the text merge). Generated files use git's text merge, so edits in different places merge cleanly; when both sides edit the same spot the restack stops with markers, and `go generate ./...` rewrites the file (`scripts/restack-regen.sh` does that for a restack, and a test runs it on a same-module conflict in these files). One package per spec file, so two route tickets in different modules edit different `<module>api/api.gen.go` files. The shared `api/api.gen.go` holds the `ErrorCode` enum, which `cmd/gen httpapi` writes one space apart: gofmt would pad every constant to the longest name, and an error code longer than the rest then rewrote all of them and conflicted with every other PR that adds a code. |
| `apps/backend/migrations/**` | Each migration is a new file with a unique timestamp name. For `atlas.sum`, a restack stops on this file with no markers (`merge=binary`); run `go generate ./...`. |
| `packages/flows/backend/**` | One file per flow, named for its id, so two tickets touch the same file only when they own the same flow. No merge driver, and `agents check` sorts nothing. |
| `.claude/skills/verify-backend/feature-map/**`, `packages/mobile-core/Tests/MonacoCoreTests/Flows/**` | `cmd/gen flows` writes one page and one outcome test file per flow, named for its id, so two tickets touch the same file only when they own the same flow. When they do, a restack stops with markers; run `go generate ./...`. |
| `apps/backend/CHANGELOG.md` | `merge=union` in `.gitattributes`. The file is hand-written and each change appends a line, and union is safe only for appended lines: an edited line comes back twice. |
| `apps/backend/internal/events/**` | Each module registers its events in its own `<module>_registrations.go`, so two modules never edit one list. |
| `apps/backend/internal/errs/codes_*.go`, `apps/backend/internal/errs/testdata/codes_*.golden`, `packages/mobile-core/Tests/MonacoAPITests/ErrorCodeCases.gen.swift` | A new feature's codes live in its own `codes_<module>_<feature>.go` and `testdata/codes_<module>_<feature>.golden`, so two features never edit one file. The table finds each file through its one `codeFiles` method, so no hand list names the files. A conflict in an existing area file `codes_<area>.go` is a real conflict: merge by hand and keep both sides' codes. The area goldens are `merge=union` in `.gitattributes` and the test reads them as sorted sets, so two appends merge cleanly, and a duplicated line or a resurrected removal fails `TestEachAreaFileDeclaresExactlyTheCodesInItsGolden`. `cmd/gen errors` writes the Swift case list one `case` per line, so two new codes conflict there only when they fall in the same alphabetical gap. The file stays on the text merge, and `go generate ./...` rewrites it whole, so run it and `git add` the file. |
| `apps/backend/internal/testkit/flows/**`, `apps/backend/internal/testkit/fakes/**`, `apps/backend/internal/testkit/scenarios/**` | New per-flow and per-scenario files. |
| `apps/backend/api/openapi.yaml` | Generated by `cmd/gen openapi` from `apps/backend/api/spec/*.yaml` and marked `linguist-generated`. A hand edit fails `scripts/ci/ready.sh`. Two route tickets in different modules edit different `spec/<module>.yaml` files, and the bundler injects the `ErrorCode` schema from the errs table, so a new error code edits no spec file and only the bundle conflicts. The bundle is one block per spec file, each with its own `# api/spec/<module>.yaml` header and its paths and components sorted, so two modules' additions land in different hunks. It merges as text: only `migrations/atlas.sum` carries `merge=binary`, and `TestGeneratedAPIFiles_stayOnGitsTextMerge` fails if any API file gains a `merge`, `diff` or `binary` attribute. `TestGeneratedAPIFiles_routesAddedToDifferentModulesMergeAsText` builds two branches that each add a route, a schema and an error code to a different module, checks that `git merge-tree --write-tree` reports no conflict, and checks that the merged tree equals a regeneration of the merged specs. A restack that edits the same spot stops with markers; run `go generate ./...`, or `scripts/restack-regen.sh`. |

## Fast and deterministic

- **Same commands as the laptop.** Every CI step calls a `just` recipe or a script the laptop also runs. CI YAML holds no test logic, so a CI failure reproduces locally with the same command.
- **No network in PR CI.** Tests use stubs for Jupiter, Privy, Helius and Pyth, as `just test backend` requires today. PR CI has no secrets, so a test that reaches for one fails instead of passing on a live service.
- **Seeds are fixed and printed.** `-shuffle=on` prints its seed. Rapid, fuzz and jitter log theirs on failure. CI sets `RAPID_NOFAILFILE=1` so it never writes to the tree.
- **Failed test databases are dropped.** `testkit.DB` drops a failed test's database on release, like a passing one, so concurrent `monacoctl agents check` runs and `just test backend` do not fill a `monaco-postgres-test` tmpfs. To keep up to 5 failed databases per run for debugging, set `MONACO_TEST_KEEP_FAILED=1`; the test log prints each kept database's URL. At start, `TestMain` drops every `t_*` and `testdb_*` database older than 15 minutes that has no connections and is not the current template, which clears databases from crashed runs. On 2026-10-04 kept databases from concurrent runs filled the 2 GB tmpfs twice (#2609). With 4 stage 0 slots, live clones alone reached about 130 databases (about 1.25 GB) plus WAL, and the 2 GB tmpfs panicked Postgres 3 times in 5 minutes on 2026-10-05. The tmpfs is now 4 GB, and the container has `restart: unless-stopped`, so a panic costs seconds instead of failing every check until someone restarts it (#2922).
- **No retries.** A failed job is not rerun to get green. A flaky test is fixed the same day or moved to nightly with an issue, per the [Testing](backend-platform.md#keeping-it-fast) rule "fixed or moved to nightly, never skipped".
- **Tight timeouts.** Each job's `timeout-minutes` is about twice its budget (`lint` 10 for a cold golangci-lint cache, `backend` 10, `e2e` 8, `mutation` 10 per package). The default is 360, which lets a hung Postgres burn six hours.
- **Caches.** `actions/setup-go` caches modules and `GOCACHE`. After checkout, reset `testdata` mtimes to a fixed date (`find . -path '*/testdata/*' -exec touch -t 200001010000 {} +`), because `go test` keys its result cache on file mtimes and a fresh checkout otherwise misses every time ([golang/go#58571](https://github.com/golang/go/issues/58571)). `golangci-lint-action` caches its own analysis. A PR can restore caches saved on its base branch and on the default branch, `staging`, but not caches from other PRs, and with no push-to-`main` run nothing would save them. So nightly gets a small Linux `warm-cache` job on `main` that builds and runs the `go` job's tests with the same flags. Because nightly runs only on `main` and every PR is based on `staging`, the full-suite `staging.yml` run on every push to `staging` also saves the module and build cache: each `backend` matrix leg ends with an `actions/cache/save` step, gated on `inputs.stage == 'staging'` and run even after a test failure, under the key `go-<os>-<go.sum hash>-<leg>-<sha>`. The PR leg of the same name restores its own leg's cache first (`backend-test-env`'s `cache-leg` input), and every other job that restores the Go cache takes the newest of any leg. The legs test under `-race`, which caches apart from a plain build, so before saving, each staging leg also runs `go build ./cmd/...` and a `CGO_ENABLED=0` build of monacoctl. Without them, the mobile integration job compiled monacoctl cold in its "List the affected flows" step (27 to 39 s when it restored a `short` leg's cache). A `prune` job in `staging.yml` then keeps only the newest `go-` cache per leg on `staging`. No separate job compiles tests just to warm the cache. Those two, and `ci-warm.yml` for the mobile caches below, are the only workflows that save caches. `backend-test-env` retries `go mod download` 3 times, so one proxy error does not fail a job. Running the tests, not only compiling them (`go test -run '^$'`), is what puts test results in the cache: `-run` is part of the result cache key, so a compile-only run never makes a PR's `go test` print `(cached)`. The `go` job's `DATABASE_URL` carries an `application_name` unique to the run. `go test` keys cached results on the env vars a test reads, so a test that uses Postgres always reruns against the migrations in the PR, and only Postgres-free packages are cached. PRs restore and never save. `ci-warm.yml` runs `ci-mobile-core.yml` with `save-cache: true` on a push to `staging`, `main` or a `backend-rewrite*` branch that changes `packages/mobile-core/**`, `apps/backend/api/openapi.yaml`, or the warm workflow. It saves the Linux job's `packages/mobile-core/.build` under `swiftpm-linux-6.3-`. It does not save an Xcode compilation cache or a Swift package artifact.
- **Few, larger jobs.** Each job pays checkout, setup and a whole-minute rounding. Split a job only when the parallelism shortens time to a result.

## Staying on the free tier

Monaco runs CI on GitHub's standard hosted runners at no cost, because the repo is public. That holds only while these rules hold:

- **Standard runner labels only.** Jobs use `ubuntu-latest`, `ubuntu-24.04`, `ubuntu-24.04-arm`, `macos-15` or `macos-26`. Larger runners (more cores, GPU, `-xlarge` macOS) are billed even on public repos, and the plan's free minutes do not cover them. `scripts/ci/check-runners.sh` fails the `plan` job when a workflow names any other label, so this rule does not depend on review.
- **Concurrency is the limit, not minutes.** The Free plan runs at most 20 jobs at once, and only 5 of them on macOS. Stage 1 and the staging indicator use one macOS slot per run, and only when the `ios` filter matches; the queue stage uses none. The nightly `qa` job is the other macOS job. If it regularly waits more than 5 minutes to start, move it to Namespace or Xcode Cloud ([When to switch](#runner-options)).
- **Artifacts and caches stay small.** Artifacts expire after 7 days on PRs and 14 on nightly. The Actions cache is capped at 10 GB per repo, and GitHub evicts the oldest entries past that, so only the nightly `warm-cache` job, the `backend` legs of the `staging.yml` run and `ci-warm.yml` save caches.
- **Public means forks.** The [Security](#security) rules apply: no secrets in PR workflows, no `pull_request_target`, no self-hosted runner.
- **Making the repo private is a CI decision.** At the measured pace the current workflows would use the 2,000 free minutes in about two weeks. Before changing visibility, land the [Rollout](#rollout) steps and the "Repo goes private" row of the switch table in the same week. Setting a $0 Actions spending limit on the account makes an overrun stop CI instead of charging the card.

## Security

The repo is public, so anyone can open a PR from a fork.

- PR workflows use `pull_request`, never `pull_request_target`. Fork PRs then get a read-only token and no secrets.
- PR CI needs no secrets. The `ios` job and the nightly `qa` job build the app with the placeholder Privy config (`scripts/ensure-ios-privy-config.sh placeholder`).
- `DOTENV_PRIVATE_KEY`, the relayer keypair and the Privy authorization key never go into a GitHub secret that a PR workflow can read.
- No self-hosted runner while the repo is public. A fork PR can run code on it and leave something behind ([GitHub hardening guide](https://docs.github.com/en/actions/security-for-github-actions/security-guides/security-hardening-for-github-actions#hardening-for-self-hosted-runners)).

## Rollout

Each step is one small PR with its own proof.

1. Gate triggers: `branches: [main]`, the `types` and `if:` above, remove the `push` trigger, add `ci-ok`, and make it the only required check. Proof: a draft PR shows no running jobs, marking it ready starts CI, and an upstack PR runs nothing.
2. Add `scripts/ci/check-runners.sh` to `plan`: it lists every `runs-on:` in `.github/workflows/` and fails on a label outside the standard set. Fold `web` into `plan`. Move `swift` to a Linux `swift` container, filtered on `packages/mobile-core/**`. Proof: a Go-only PR runs no macOS job, and a planted `runs-on: ubuntu-latest-4-cores` fails `plan`.
3. Tighten `timeout-minutes`, add the `testdata` mtime reset, add the nightly `warm-cache` job, and stop PRs saving caches. Proof: a second run of an unchanged PR shows cached test results in the `go test` output.
4. Nightly skips when `main`'s head equals the head SHA of the last successful nightly run (`gh run list --workflow nightly.yml --status success --limit 1 --json headSha`). Proof: a manual dispatch on an unchanged `main` exits in the first step.
5. At backend-platform Rollout step 1, replace the `go` job with `backend`, `e2e` and `mutation` as above, and set each budget from the times the scaffold measures in CI.
